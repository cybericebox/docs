Platform 2.20 is the part of Cyber&nbsp;ICE&nbsp;Box that runs events, the task catalog and accounts on top of the Laboratory. This release
goes with Laboratory 1.10 and agent API contract 3.0. The task format is now `cib-exercise/1.0`: VPN and internet gateways are devices of
the task, a lab may have several of them, and a task can have lab checks and a console in the browser. Lab devices open with a signed
grant instead of a link with a token. Accounts get passkeys and a safer Google sign-in. The files the platform stores are encrypted, and
one master key can replace the separate keys. The platform panel gets a dashboard and new tables for users, events, the audit log,
notifications and infrastructure. The backend repository is renamed from `daemon` to `backend`. Read the Upgrade section before you install:
this release is not backward compatible and the upgrade is not rolling.

## Requires

- **Laboratory 1.10** (agent API contract 3.0). Older laboratories are not supported, and Laboratory 1.10 does not work with an older
  platform. Upgrade the laboratory first, as its [release page](/en/releases/laboratory/1.10/) describes.
- **The backend image is `cybericebox/backend`.** The repository was renamed from `daemon` to `backend`. Images before 2.20 stay in
  `cybericebox/daemon`; 2.20 and later are published only as `cybericebox/backend`.
- PostgreSQL. The database migrations run by themselves when the backend starts.
- An S3-compatible files bucket that the deploy creates, with a rule that expires non-current object versions (for example after 30 days).
  The backend no longer creates the bucket.
- A key for the files: `SECRETS_MASTER_KEY` (or `SECRETS_MASTER_KEY_DIR`), or `FILES_SECRETS_KEY`. With storage configured, the backend
  does not start without it.
- The backend, ID, platform panel, task catalog, event site and landing of the same release.

## Backend

Platform 2.20 needs Laboratory 1.10 (agent API contract 3.0). The repository is renamed from `daemon` to `backend`, and the image is now
`cybericebox/backend`; images before 2.20 stay in `cybericebox/daemon`. The program inside the image keeps its name and its commands.
Database migrations run automatically on start. The upgrade is not rolling: stop every old replica before the new one starts (see
"Before you upgrade" below).

### Tasks and the catalog

- **New task format `cib-exercise/1.0`.** Stored task versions are converted automatically. An archive with the old schema string
  `cib-exercise/1` is refused at import with an error that names the new one; export it again from a 2.20 catalog or update its schema.
  An import always lands as a draft, with exactly one version.
- **Gateways are devices.** VPN and internet gateways are devices of the task with their own settings (DHCP, DNS, reverse connections),
  up to 10 per variant and at most one per network. Placeholders in descriptions name the gateway they take an address or subnet from.
- **Node profiles.** A device is a node with a profile (container, microVM, VM) instead of the old container type. A platform setting
  (node profiles) chooses which profiles the catalog accepts; only containers are allowed by default. State persistence is refused on microVM
  and VM devices.
- **Access list per device.** One list of access kinds (web page, console) replaces the separate external and terminal fields. A device
  link in a task description opens the access kind the author chose.
- **Lab checks.** A task can be checked inside its lab. Participants can start a check of their own task, with a limit per team and task.
  A device whose service the laboratory starts must name the user of that service; publishing refuses an image whose user is unknown.
- **Images are pinned by digest** when a task is imported or published; a draft save never fails because of a registry. Registries of
  user-supplied images are reached over HTTPS only.
- **Secret variables without a value** are listed per version, and publishing waits until they are entered.
- **Concurrent edits.** Every write to a draft carries the revision it started from. A stale write is refused and says who saved the
  draft and when, so two authors no longer overwrite each other.
- Stricter checks: the device names `vpn`, `gateway`, `internet`, `ctl` and `ctl-switch` are reserved; a variant weight is 1 to 100;
  descriptions and hints may not contain answer or variable substitutions; a flag template accepts a repeat count `{n}`.
- A catalog import survives a backend restart and resumes; failed rows are listed and can be closed.

### Labs and stands

- **Device access with a signed grant.** The backend signs a short grant for one device with the tenant key, and the page posts it to the
  laboratory. No token goes into a link any more. No grant is issued once the event has finished.
- **Faster launch.** The first stand deploy waits for the image cache prewarm (at most `EXERCISE_STAND_PREWARM_WAIT`, 10 minutes, never past
  the start), and labs are handled in parallel (`EVENT_LAB_LIFECYCLE_WORKERS`, 16).
- A failed lab is recreated by itself up to three times (after 1, 5 and 15 minutes) before the stand fails and the organizers are told.
- A stand is prepared only for a formed team. A waiting lab says what it waits for.
- With a resource calendar, the end of the reservation window is the only point where labs are deleted; the reservation may not end after
  the withdrawal of the event.
- A lab with a device that keeps state is always stopped with a snapshot.
- Updating a task set keeps the board rows and recreates only the labs whose content changed, after the organizer confirms.
- The laboratory's feature switches and allowed registries are read up front: a task that needs a switched-off feature is refused early
  with a clear reason.

### Events and organizers

- One readiness view before the start: tasks that are not published and stands that are not ready.
- Organizers see which team copies of a task differ from the task and can sync them (text, files, hints).
- Organizers can move a member to another team, change the captain, accept an invitation for a participant and correct an invitation
  address.
- Every change of the event schedule is recorded with who, when and from what to what.
- A per-participant report of flag submissions, with CSV export.

### Accounts and sign-in

- **Passkeys.** A passkey is a sign-in method of its own, next to the password and Google. A cloned key is flagged as compromised.
- **Google sign-in.** A Gmail account links at once; another domain confirms with the password or a code sent by mail. Google sign-in never
  matches an address that is not confirmed.
- The sign-in page can remember the last address, only with functional cookie consent.
- People can download their own data as a JSON file. Deleting an account also revokes its reset, email-change and setup codes.
- Account creation records the documents the person accepted. `TERMS_URL` and `PRIVACY_URL` (optional) set the Terms and the Privacy
  Policy; a document that is not set is not linked and not required. `MAIN_SITE_URL` (optional) is the site address in mail footers.

### Platform panel API

- One dashboard answer by permission; users and events tables with filters, counts and bulk actions; per-person table views.
- The audit log records what each action changed and exports CSV. Error groups can be resolved, ignored or reopened in bulk.
- Broadcasts can be cancelled; failed deliveries can be resent in bulk; the delivery log can be searched by recipient and period.
- Analytics can compare with the previous period.

### Keys and security

- **One master key.** `SECRETS_MASTER_KEY` (or `SECRETS_MASTER_KEY_DIR`, a versioned keyring) derives the key of every purpose (platform,
  VPN, task, session, files, setup links, OAuth state). The existing per-purpose keys still load, so data sealed before keeps opening.
  Without a master key nothing changes. The backend commands `keys status`, `keys check` and `keys reencrypt` show the keys
  in use and move stored secrets to the current key.
  `SECRETS_GUARD` (`warn` by default) decides what start-up does when a stored value names a key that is not loaded.
- **Encrypted files.** Every object in the files bucket is encrypted, except public images. Existing files are moved to encrypted objects
  by a background job; nothing has to be run by hand.
- `RENDER_SECRET_NEXT` lets the render secret change without a gap.
- **The client address comes from the connection only.** `TRUSTED_PROXIES` and the PROXY protocol are gone. `CF-Connecting-IP` is used
  only on a connection with a verified client certificate (`HTTP_SERVER_TLS_CLIENT_AUTH`, `HTTP_SERVER_TLS_CLIENT_CA_FILE`).
- Optional: the backend can pass the TLS traffic of the frontend hosts on to their services by server name (`HTTP_SERVER_ENTRY_*`, off by
  default).

### Configuration

- New, optional: `SECRETS_MASTER_KEY`, `SECRETS_MASTER_KEY_DIR`, `SECRETS_GUARD`, `FILES_SECRETS_KEY`, `MAIN_SITE_URL`, `TERMS_URL`,
  `PRIVACY_URL`, `RENDER_SECRET_NEXT`, `EXERCISE_STAND_PREWARM_WAIT`, `EVENT_LAB_LIFECYCLE_WORKERS`, `HTTP_SERVER_ENTRY_*`.
- Removed: `TRUSTED_PROXIES` and `LAB_ACCESS_TOKEN_TTL`. Remove them from your settings.
- Deprecated: `JWT_TOKEN_SIGNATURE` and `OAUTH_STATE_SIGNATURE`. With a master key they only verify links already sent and can go once
  those have expired.
- The default database pool is 24 connections (`POSTGRES_MAX_CONNS`).
- The `BRAIN_*` settings connect an optional external authoring assistant. It is off while they are unset.

### Before you upgrade

- Upgrade Laboratory 1.10 first.
- Make sure the files bucket exists and expires non-current versions, and that a files key is set.
- Stop every old replica before the new one starts. A backend before 2.20 cannot read an encrypted file, so do not roll back once the new
  one has run.

### Notable fixes

- A request cancelled by a client that left answers 499, not a server error.
- The leader keeps its role under load: its session check has its own timeout.
- The participant board and lab status are never cached, so a stale address is refreshed.
- Removing a task set no longer fails the lifecycle of the whole event; destroying a test lab no longer fails on a stale lab.

## ID

Works with the backend of Platform 2.20.

- **Google sign-in confirmation.** When a Google account is linked to an existing account, a screen shows both accounts and asks for the
  password or a code sent by mail, with a resend countdown, a bot check and a "Not you?" link.
- **The sign-in form remembers the last address** and offers "Not you?" to change it. This needs consent to functional cookies.
- **Cookie consent.** The "Functional" category now controls functional storage in ID (drafts, the back link, the inbox mark, the last
  address). The banner texts follow the cookie policy.
- **Account setup.** The acceptance checkbox follows the documents the installation sets: the Terms, the Privacy Policy, both or neither.
- **Installation settings.** The logo, the footer links, the cookie policy link and the department line follow the optional settings
  `NEXT_PUBLIC_MAIN_SITE_URL`, `NEXT_PUBLIC_TERMS_URL`, `NEXT_PUBLIC_PRIVACY_URL`, `NEXT_PUBLIC_COOKIES_URL` and
  `NEXT_PUBLIC_SHOW_ICE_DEPARTMENT_SUPPORT`. A link that is not set is not shown. `NEXT_PUBLIC_SHOW_PARTNERS` is removed.
- Menus mark a choice the same way everywhere: a dot for one of many, a checkbox for several.
- Dependencies are updated (Next.js 16.4, React 19.3).

## Platform panel

Works with the backend of Platform 2.20.

- **Dashboard.** An attention list, what runs now and soon, 7-day trends, infrastructure and quick actions.
- **Users.** One table with filters in the address, pinned columns and bulk actions. The user card shows participations and sessions, can
  end sessions and resend an invitation.
- **Events.** A table with counts, filters and bulk archive. A new event can be created as a copy of another one, with an exact list of
  what the copy takes.
- **Tables.** Columns can be moved, hidden and resized, filters combine with counts, and each person's view of a table is saved on the
  server.
- **Audit log.** Filters as chips with quick presets, what each request changed, and CSV export.
- **Errors and requests.** Error groups can be resolved, ignored or reopened in bulk. Resource requests show the free cluster capacity, the
  author's history and a pending badge in the menu.
- **Notifications.** The delivery log has filters, search by recipient and period, and bulk resend. Broadcasts can be copied and cancelled,
  with paged deliveries and CSV. The template editor shows the difference between versions. Turning off sign-up, sign-in and invitation
  messages asks first.
- **Analytics.** A custom date range, comparison with the previous period, auto-refresh and server-side paging, search and sort of the
  people, events and task tables.
- **Infrastructure.** Tabs for stands, test labs, the current state and capacity, with bulk recreate and terminate; an agents summary with a
  separate menu for dangerous actions. The agent settings have one grant lifetime instead of the token and session lifetimes.
- **Settings.** Key descriptions come from the backend and can be searched. Data retention has a term for participant telemetry.
- **Privacy.** Google Analytics loads only after analytics consent. The "Functional" category controls functional storage (table
  views, the return address, the inbox mark).
- **Installation settings.** The logo, the cookie policy link and the home button of the no-access screen follow `NEXT_PUBLIC_MAIN_SITE_URL`
  and `NEXT_PUBLIC_COOKIES_URL`. The retention comparison file is optional (`NEXT_PUBLIC_RETENTION_URL`).
- Dependencies are updated to fix security advisories.

## Task catalog

Works with the backend of Platform 2.20 and Laboratory 1.10.

- **New task editor for `cib-exercise/1.0`.** The editor is rebuilt for the new task format: general data and variants, subtasks,
  infrastructure, the test lab, and import and export. The header shows the status (draft, published, archived) and an always visible
  save indicator.
- **Gateways.** A lab can have several VPN and internet gateways, placed as devices on the schema. The editor shows the gateway limit of
  the platform, and placeholders take an address or a subnet from a chosen gateway.
- **Test lab.** The author's test lab opens with a signed grant instead of a link with a token, in a new tab or in the console frame. The
  console frame accepts only the console host of the lab. Extra lab domains of other agents are allowed with `NEXT_PUBLIC_LAB_DOMAINS`.
- **Errors at their fields.** Errors from the backend appear beside the field they belong to and disappear when it changes. A publish or
  a test run after a refused save opens the list of problems at the field. Error texts follow the backend catalog.
- **Concurrent edits.** Every draft write carries the revision of the working copy, so a save over someone else's newer changes is refused
  instead of overwriting them.
- Restoring unsent edits keeps the stored values of variables; a new secret row stays in the draft and publishing asks for its value.
- The device table of the infrastructure editor stays readable on phones, and the editor tab row keeps the selected tab in view.
- **Installation settings.** The logo, the cookie policy link and the no-access home button follow `NEXT_PUBLIC_MAIN_SITE_URL` and
  `NEXT_PUBLIC_COOKIES_URL`; a link that is not set is not shown.
- Dependencies are updated (Next.js 16.4, React 19.3).

## Event site

Works with the backend of Platform 2.20 and Laboratory 1.10.

- **Lab devices open with a signed grant.** The page posts a short grant to the device instead of opening a link with a token. Extra lab
  domains of other agents are allowed with `NEXT_PUBLIC_LAB_DOMAINS`.
- **Several gateways per lab.** The lab status and the placeholders of a task follow the lab's gateways: a subnet or an address is taken

- Links in banners, the inbox and rich text are checked in one place, and markup is stripped fully in the notification editor.

## Upgrade

Platform 2.20 and Laboratory 1.10 are released together and are not compatible with earlier versions. Upgrade between events.

1. **Upgrade the laboratory to 1.10 first**, following its [release page](/en/releases/laboratory/1.10/): Kubernetes 1.35, node pools, load
   balancers, the new values and the custom resource definitions. In the laboratory values, list the origins of the platform pages (the
   event sites and the task catalog) in `proxy.l7.platformOrigins`.
2. **Change the backend image** from `cybericebox/daemon` to `cybericebox/backend` with the 2.20 tag.
3. **Prepare the files bucket.** It must exist (the backend no longer creates it) and must expire non-current object versions, or the
   plain copies of files that were moved to encrypted ones stay readable.
4. **Check the settings.**
   - Set a files key: `SECRETS_MASTER_KEY` (recommended; it can replace the per-purpose keys) or `FILES_SECRETS_KEY`. Keep the
     per-purpose keys you already have: data sealed with them must keep opening.
   - Remove `TRUSTED_PROXIES` and `LAB_ACCESS_TOKEN_TTL`. If a proxy in front of the backend gave the client address in a header, that
     address is no longer read: let clients reach the backend directly or through a pass-through load balancer that keeps the client
     address.
   - Optional: `TERMS_URL`, `PRIVACY_URL`, `MAIN_SITE_URL` for the backend and the matching `NEXT_PUBLIC_*` settings of the frontends.
     Remove `NEXT_PUBLIC_SHOW_PARTNERS`.
5. **Stop every old backend replica**, then start the new backend. The database migrations, including the conversion of stored tasks to
   `cib-exercise/1.0`, run by themselves on start. Do not roll back to an older backend afterwards: it cannot read encrypted files.
6. **Upgrade the frontends**: ID, platform panel, task catalog, event site and landing of this release.
7. **Recreate the labs** that were created before the upgrade, as the laboratory page says. Participants open their device links again.
8. **Task archives.** Archives with the old schema string `cib-exercise/1` are refused at import. Tasks already in the catalog were
   converted; export them again to get `cib-exercise/1.0` archives.
