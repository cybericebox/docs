Laboratory 1.10 is a large release of the part of Cyber&nbsp;ICE&nbsp;Box that runs the labs. It adds a browser console for devices, lab checks,
several VPN and internet gateways per lab, finer VPN access, feature switches for the cluster and for each lab group, and a registry gate that
checks the credentials of every image pull. The installation changes too: the nodes are split into two pools, and the laboratory is reached
through NodePort Services behind load balancers instead of a Gateway. This release is not backwards compatible. It needs Kubernetes 1.35, the
platform backend and frontends released together with it, and labs created before the upgrade must be created again. Read "Upgrade" before you
install it.

## Laboratory

### Requirements and compatibility

- **Kubernetes 1.35 or newer** (it was 1.33). The registry gate relies on the kubelet checking the pull credentials of a pod (KEP-2535, on by default
  from 1.35). The chart refuses an older cluster. `kubectl` 1.35 or newer is needed as well.
- **Management agent API contract 3.0** (1.9 had 1.4). Lab groups, labs, access, checks and features changed in ways an older backend cannot use.
  There is no compatibility layer: the laboratory, the platform backend and frontends and the infrastructure are upgraded together.
- The chart is published as an OCI chart at `oci://registry-1.docker.io/cybericebox/laboratory`. The images are `cybericebox/laboratory-controller`,
  `-agent`, `-proxy`, `-node` and `-lab`, for `linux/amd64` and `linux/arm64`. The chart uses the images of its own version.

### Browser console of a device

- A participant can open a shell in a device from the browser. The console is off by default (`terminal.enabled`). When it is on, the chart installs
  the **device access service** (`laboratory-device-access`, a DaemonSet on the lab nodes). It is the only component that talks to the container
  runtime, and only the L7 proxy can reach it.
- The console supports copy and paste. File transfer is not available.
- The console uses no cookies, and the platform page can show it in a frame. The sites that may embed it are set in `terminal.embedding`. Open
  consoles are limited per participant, per lab and per node, and each console has an idle time and a maximum lifetime (8 hours by default).

### Browser access to devices

- Each device has a list of access methods (`http`, `terminal`). It replaces the old `external` and `terminal` fields.
- **Device host names change.** A device host is `<device>-<code><kind>`, where the last letter is the kind of access (`w` web, `t` console).
  Clients take the address from the access list of the device and never build it themselves.
- **A web session is a grant signed by the tenant.** The platform signs a short grant for one device host with the access key of its tenant. The
  proxy checks it with the tenant's public key and keeps no secret of its own. After the grant is accepted, the browser gets a host-only cookie
  (`__Host-cib_grant`) for that one device host. A cookie from another host is refused. The longest grant is `proxy.l7.grantMaxTTL` (8 hours),
  and only the origins in `proxy.l7.platformOrigins` can post a grant.
- Session cookies of earlier versions, which were valid for the whole lab domain, are refused. A participant opens the device link again.
- Opening links is rate limited per client address. Only links that pass verification count.
- RDP and VNC access are reserved and stay off (`proxy.rdp.enabled`, `proxy.vnc.enabled`).

### Lab checks

- A lab can have checks that the laboratory evaluates inside its devices. Checks are off by default (`checks.enabled`). When they are on, the chart
  installs the **checker** (`laboratory-checker`, a DaemonSet on the lab nodes, separate from the node-agent).
- Built-in read-only observations are `file`, `directory`, `process`, `port`, `kernel_param`, `request` and `permission`. A `custom` check
  runs a command of the author as an unprivileged user with a clean environment. The expected answer is never sent to the device.
- Results are written to the status of the lab. The platform can also start a run on request (`RunChecks`). Limits: `checks.maxConcurrent` (4 runs
  at once on a node), `checks.maxTimeLimitSeconds` (120) and `checks.manualCooldown` (10 s between manual runs).
- A device whose service is started by the laboratory (a bootstrap or a service command) must name the user of that service. A device without one
  is refused. Before, such a service silently ran as root even when the image used an ordinary user.

### Networks, VPN and internet

- **Several gateways per lab.** A lab lists its gateways in `spec.gateways`: VPN gateways and Internet gateways, up to `operator.maxLabGateways`
  (10) in total, with at most one gateway per broadcast domain. This replaces the `spec.vpn` and `spec.internet` fields, which are removed.
- One address network for all gateways, `operator.labBaseNetwork` (default `10.128.0.0/9`), replaces `vpnBaseNetwork` and `inetBaseNetwork`.
  An existing address pool of a group is grown in place.
- **Finer VPN access.** An access rule names a client, the labs and the VPN gateways it opens, and can be narrowed to subnets inside a gateway. The
  WireGuard configuration of a client allows exactly the addresses it can reach. A rule that names no VPN gateway opens no VPN.
- A client can have browser access only, without a WireGuard peer.
- **Internet per device.** A device can be denied the internet. Such a device cannot share a network with an Internet gateway, and the lab is
  refused rather than started with the device online.
- A lab cannot start connections towards VPN clients unless its VPN gateway allows it (`reverseConnections`). The blocked attempts are counted for
  the administrator.
- **Switches for each lab group.** A group runs its VPN server and its internet gateway only while `spec.vpn.enabled` and `spec.gateway.enabled`
  are on. A lab that needs a server that is off is refused with a clear reason, and a server that a lab still uses cannot be turned off. Groups
  created before this release keep both servers on.
- The traffic of the internet gateways is reported through a new resource, `LabEgressReport`. The statistics page of the gateway and its port
  (`statsPort`) are removed.

### Feature switches and allowed registries

- What a cluster offers is set once in the chart: `vpn.enabled`, `inetGateway.enabled`, `proxy.enabled` and `proxy.l7.enabled`,
  `terminal.enabled`, `checks.enabled` and `scheduler.enabled`. A lab that needs a feature that is off is refused with a stable reason
  (`VPN_UNAVAILABLE`, `INTERNET_UNAVAILABLE`, `ACCESS_UNAVAILABLE`, `CHECKS_UNAVAILABLE`).
- The refusal comes from the Kubernetes API server itself, so it also holds for objects created with `kubectl`. The management agent and the
  operator refuse the same labs. The backend reads the current state with `GetFeatures`.
- `registry.allowedRegistries` lists the registries lab images may come from (default `docker.io`, `ghcr.io`, `quay.io`, `registry.k8s.io`).
  An image from any other registry is refused (`REGISTRY_NOT_ALLOWED`) until its registry is added.

### Images and the registry gate

- **A registry gate stands in front of the image cache.** Every pull is checked against the upstream registry with the credentials of the tenant
  that asks for it, so a tenant cannot pull another tenant's private image from the cache. No lab node and no lab pod holds a registry credential.
  The credentials sit in the namespace `laboratory-upstream`, which only the gate reads.
- The image cache is on by default and required on clusters with lab nodes. Every registry a lab may use must be served by the cache: the four
  built-in registries, plus others listed in `registry.cache.extraRegistries`.
- **Images are pinned to digests.** A tag is resolved to a digest when the lab is created (`registry.cache.requireDigest`, on by default). A tag
  that cannot be resolved makes the lab creation fail and the error names the image.
- `registry.cache.redirects` lists the hosts a registry may redirect to. `registry.k8s.io` → `*.pkg.dev` is built in.
- The gate checks each layer against its digest while it is stored, follows redirects only to public host names, and never shows the text of a
  registry's answer in a status, an event or a log.
- Registry credentials without a username are refused while the cache is on (`CREDENTIAL_NOT_SUPPORTED`).
- The cache can be warmed in advance with `PrewarmImages`. The warming goes through the gate with the caller's credentials.
- Known limit: the kubelet remembers which credentials pulled an image until the image leaves the node. Set `imageMaximumGCAge` on the kubelet
  (for example `24h`) so that unused images are removed.

### Nodes and how the laboratory is reached

- **Two node pools.** Nodes are labelled `node-restriction.kubernetes.io/cib-pool=lab` (labs, node components and the proxies) or `=lab-control`
  (the operator, the agent, the scheduler and the registry). A node cannot set this label itself. The selectors are fixed in the chart. A
  `nodeSelector` in the values is refused. Only the tolerations can be set (`pools.lab.tolerations`, `pools.labControl.tolerations`).
- **No Gateway.** The L7 proxy (TCP 443), the management agent, the VPN (UDP 51820) and the registry gate (TCP 5443, internal) are `NodePort`
  Services with `externalTrafficPolicy: Local`, behind load balancers made by the infrastructure. The `gateway.*` values are removed.
- The proxy takes the client address from the TCP connection. PROXY protocol is no longer used.
- **node-state.** Device snapshots and the CPU throttle monitor move from the node-agent to a separate DaemonSet, `laboratory-node-state`. It is
  installed only when device state persistence or runtime observation is on. The node-agent loses the privileges these tasks needed.

### Speed, metrics and activity

- Labs start faster: the operator runs several workers at once (`operator.workers.*`: Lab 8, Device 16, Connection 8), talks to the API server
  faster (`operator.api.*`: 200 requests per second, bursts of 400), and resolves image digests in the background. The agent creates labs of
  different groups in parallel. The default operator limits are 2 CPU and 512 MiB.
- The agent runs one replica by default. The chart refuses more unless `agent.multiReplicaAck` is set.
- Metrics endpoints for the operator, the node-agent and the agent, off by default (`operator.metrics`, `nodeAgent.metrics`, `agent.metrics`).
  They show where the time of starting a lab goes.
- **Activity reports**, off by default (`activityReports.enabled`): raw facts about lab activity (internet traffic of the gateways, console
  sessions, devices reached over the VPN), kept for at most one hour in the cluster. The laboratory gives them only to its own platform, through
  `GetLabGroupActivity`, and sends nothing anywhere by itself.

### Bandwidth protection

- Bandwidth protection is now on by default (`bandwidth.enabled`).
- A participant gets at most 20 Mbit/s and at least `bandwidth.caps.participantMinKbps` (1000 kbit/s), so a console session keeps working on a
  busy node.

### Notable fixes

- The containerd libraries are updated to 2.4.2, which fixes a crash on a malformed image digest (security advisory).
- A node check whose reason code contains digits (for example `CGROUP_V2_MISSING`) was refused by the admission policy. It is accepted now.
- A failure inside the snapshot engine fails only the affected device, not the whole node. Snapshot work on a node has limits for parallel
  comparisons and temporary space.
- Two silent integer overflows, in an offset and in a status filter, are fixed.

## Upgrade

The laboratory, the platform backend and frontends and the infrastructure are released together. Upgrade between events, and plan to create the
running labs again. A rollback of the laboratory alone is not supported; it works only together with the earlier backend and frontends.

1. **Kubernetes 1.35 or newer** on every node, and `kubectl` 1.35.
2. **Label the nodes** with `node-restriction.kubernetes.io/cib-pool=lab` or `=lab-control` before the upgrade. A node without the label gets
   no pods. Set the tolerations of the pool taints in `pools.lab.tolerations` and `pools.labControl.tolerations`.
3. **Load balancers.** Point the load balancers at the `NodePort` Services of the proxy, the agent, the VPN and the registry gate. The load balancers
   must keep the client address. Set fixed node ports in the values if your load balancer needs them.
4. **Values.**
   - New required values: `registry.gate.address` (the internal address the lab nodes use to reach the registry gate) and
     `proxy.l7.platformOrigins` (the origins of the platform pages).
   - Remove the values that no longer exist: `gateway.*`, `proxy.sharingKey`, `proxy.sharedNamespaces`, `proxy.service`, every `nodeSelector`
     of a component, `vpnBaseNetwork` and `inetBaseNetwork` (now `operator.labBaseNetwork`). The chart refuses the ones it cannot ignore.
   - Every registry in `registry.allowedRegistries`, and the registry of every platform image, must be served by the cache
     (`registry.cache.extraRegistries`). `"*"` is refused.
   - The agent runs one replica. To keep more, set `agent.multiReplicaAck: true`.
   - Tenant registry credentials (`tenants.<name>.images.pullSecret`) need a username.
5. **Apply the custom resource definitions first.** `helm upgrade` does not update them. Take them from the chart of this release:

   ```bash
   helm pull oci://registry-1.docker.io/cybericebox/laboratory --version 1.10.0 --untar
   kubectl apply --server-side -f laboratory/crds/
   ```

   This release adds `LabActivityReport` and `LabEgressReport` and changes most of the others.
6. **Upgrade the chart.** One `helm upgrade` installs the registry and the node-agent in the right order:

   ```bash
   helm upgrade laboratory oci://registry-1.docker.io/cybericebox/laboratory --version 1.10.0 \
     --namespace laboratory-system -f my-values.yaml
   ```

7. **Create the labs again.** Image references now carry the tenant, and device host names have changed. Labs, VPN pods and gateway pods created
   before the upgrade fail at their next image pull. Participants open the device links again.
8. Optionally, set `imageMaximumGCAge` on the kubelets (see "Images and the registry gate").

The full upgrade notes are in `DEPLOY.md` of the laboratory repository, section "Upgrading to the pools release".
